# A 最初の概観（`dataset_overview`）設計

- 日付: 2026-11-06
- 関連: [全体](2026-11-06-overhaul-overview-design.md)、B [統一データセットとツールの統合](2026-11-06-unified-dataset-and-tools-design.md)、
  C [統計エンジン](2026-11-06-statistics-engine-design.md)。
- 状態: 利用者と合意した設計（2026-11-06）。未実装。順番は B → C → A → D の 3 番目。

## 1. 目的

データを開いた時点で、頼まれなくても「群の間で何が変わり、何が変わっていないか」に粗く答える。
問いを持たない利用者には、データの特徴と言える事実を示す。問いを持つ利用者には、問いに入る前の地図になる。
最初の応答は粗くてよく、そこからツールを対話的に使って掘り下げられるようにする。

今の `load_dataset` は `.arf2` の概観と前処理前の PCA を返す。前処理前の PCA は要らない（利用者の判断）。

## 2. 目標・非目標・反目標

目標:

- `dataset_overview` ツール。`load_dataset` は読み込みの最後にこれを 1 回呼ぶ。鎖を進めた後（キュレーション・換算・統合・選別の後）にも
  呼び直して、同じ形の概観を出し直せる。
- 粗い順に 4 段（品質 → 全体 → クラス → 分子種）で答える。
- 各段に「ここを掘るなら」の次の一手（ツール名と引数）を 1 行で添える。
- 事実に ID を付け、考察（LLM が書く）が根拠の事実を挙げられるようにする。

非目標:

- 考察そのものをサーバが書くこと。
- 図を最初の応答に入れること（§6）。
- 問いに沿った比較（`dataset_compare` など C のツールの仕事）。

反目標:

- 品質に問題があるのに、差の話を先に出す。
- 「有意でない」を「変わっていない」として示す（C §7 の判定だけを使う）。
- 群の名前から対照を推測して、向きを決めたように見せる。
- 戻り値が長くなり、結論が埋もれる（CLAUDE.md の戻り値を太らせない規則）。

## 3. 状態の表示

冒頭に、データセットがいまどの段階にあるかを書く。

- 入口（解析フォルダ・mzTab-M・pipeline の run）、極性、試料の数（役割ごと）、特徴の数、同定の証拠の水準ごとの数、`assay_kind`。
- 鎖のどの工程が済んでいるか（キュレーション・内部標準の換算・統合・選別。B §6）。
- まだ済んでいない工程があれば「暫定（キュレーション前・換算前）」と明記する。読み込み直後の概観は必ずこれになる。

## 4. 4 つの段

各段は数行と上位数件（TSV）にとどめる。全量は結果の登録（C の結果）に置く。

### 4.1 品質

差の話より先に置く。悪ければ「差を語れる状態か」をここで示す。

- QC の RSD の分布（中央値、RSD 30% 以下の特徴の割合）、失敗した QC の検出（今の `detect_failed_qc`）。
- 実検出率と gap-fill の割合（B の `detected_mask`。取り込めないときは「評価できない」と書く）。
- ドリフトの兆候（QC の注入順と主成分や総量の相関）。
- 群 × バッチ・注入順の交絡（C §9）。
- QC やブランクが無いとき、品質の評価ができないことをそのまま書く。

### 4.2 全体

- 群がそもそも分かれているか: 前処理後の PCA（C §10）の寄与率と、群の重心の位置の要約（数字だけ。図は §6）。
- 「どれかの群で差があるか」の moderated F（C §6）で、差がある特徴の数。2 群なら 2 群の比較の判定ごとの件数。

### 4.3 クラス

- クラスごとの合計の変化（効果量・95% 区間・判定）と、組成（CLR。C §11）の変化。変わったクラスと、変わっていないクラスの両方を挙げる。
- `assay_kind` が `lipid` 以外のときは「MS-DIAL のオントロジー」として表示する。クラスの情報が無ければこの段は省き、そう書く。
- **付加体の選別（B §6.2 の 4）が済むまで、この段は出さない**（私の判断）。選別の前は、内部標準の行（一定量を添加した標識体）と
  1 分子種の複数の付加体がクラスの合計に入り、効果量が 0 に寄って見せかけの `unchanged` が出るため。読み込み直後の暫定の概観では、
  省いた理由と、選別へ進む次の一手を書く。

### 4.4 分子種

- 判定ごとの件数（`changed` 上昇・下降、`unchanged`、`inconclusive`）と、出方だけが違う特徴の数（C §5）。
- 変わった上位数件（名前・同定の証拠の水準・効果量と区間・q）。

## 5. 群の扱い

- 群は試料の情報（MS-DIAL の Class ID、または `dataset_set_sample_metadata` で直した値）から取る。QC・Blank は群に入れない。
- 2 群: その 2 群を比べる。どちらを対照にするかは推測しない。仮の向き（並びの順など）を明記し、向きを決める次の一手を添える（私の判断）。
- 3 群以上: moderated F で「どれかで差がある」特徴を数え、その特徴について、どの群の対の間で差が出ているかの件数の表を示す。
  対照を決めた比較は、候補の対比として次の一手に並べる。
- 2 因子の構造（処置 × 時点など）は、利用者が因子を指定したときだけ使う（Class ID は 1 つの文字列なので）。
- 個体 ID（`subject_id`）があれば反復注入をまとめる（C §6）。無いのに反復注入らしい試料名があれば、品質の段で知らせる。

## 6. 図

最初の応答には図を入れない（画像は 1 枚数百トークンかかるため）。PCA・volcano・クラスの図は、次の一手として
`dataset_plot` の `kind` と引数を示す。

## 7. 前処理の既定

- 概観は C の既定の前処理（C §4）で計算し、使った recipe を状態の表示に書く。
- 内部標準で換算済みで、ドリフト補正の既定が決まっていない（C §4 で利用者に尋ねる場合）ときは、概観はドリフト補正なしで計算し、
  その旨と、決めるための次の一手を書く（概観は止まらない。私の判断）。

## 8. 事実の ID と考察

- 各段の事実に ID を付ける（例 `Q1`、`G1`、`C3`、`S2`。形は実装者に任せる）。事実は「条件付きの数字」として書く
  （どの前処理・どの比較・どの判定の幅か）。
- 概観の事実は結果の登録に保存し、後から `write_report` などで引用できるようにする。
- 考察はサーバが書かない。`MCP_INSTRUCTIONS`（`metabolomix/core/mcp_core.py`）に、考察は根拠の事実の ID を挙げて
  事実と別の欄に書くこと、を足す。

## 9. 次の一手

各段の末尾に 1 行で添える。例:

- 品質: `dataset_plot(kind="pca", color_by="batch")`、`dataset_exclude(samples=[…])`
- 全体: `dataset_compare(groups=[…], reference=…)`
- クラス: `dataset_plot(kind="group_intensity", items=[…])`
- 分子種: `dataset_feature_search(feature_ids=[…])`、`dcl_spot_spectrum(spot_id=…)`

ツール名と引数は B・C で決まった名前に合わせる。

## 10. 出力の大きさ

最初の応答の目安は 1,500 トークン程度まで（私の判断。実データで測って決め直してよい）。行の一覧は TSV（列名 1 回）、
float は丸め、`json_payload()` で返す（CLAUDE.md の規則）。

## 11. 問いを持ち込む使い方とのつながり

利用者が問い（例「群 A と B で膜脂質の組成がどう変わったか」）を持っているときも、概観は中立に出す。
問いへの答えは、LLM が `dataset_compare`（組成なら C §11 の解析）を呼んで出す。`record_objective` で記録した問いの群や
クラスがあれば、概観の次の一手をそれに合わせて並べてよい（並べ方は実装者に任せる）。

## 12. 実装者に任せること

- 事実の ID の形、各段の行数と上位件数。
- 2 群の仮の向きの決め方。
- 重心の位置の要約の数字の選び方。
